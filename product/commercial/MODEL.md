### 与「开发用自备密钥」的关系（不冲突）

| 场景 | 策略 |
|------|------|
| **对外产品 / 付费用户** | 平台统一提供智能服务与计费；用户**不必**也不应配置底层密钥 |
| **内部开发 / 联调** | 可使用自备密钥通道，仅方便研发，**不是**对外卖点，不写进产品定位主叙事 |

## 一、我们卖什么

用户购买的是：

> **帮我把这批浏览器里的重复劳动做完，并拿到可核对、可带走的结果文件。**

用户**不**购买：

- 按 token 计价的模型转售  
- 「Mana」等抽象游戏币感货币（首发不建议）  
- 自己挑选底层模型供应商并比价  
- 开发者密钥托管服务  

因此：**任务 / 任务包 / 套餐内额度**是主计价单位；软件业务需要健康毛利，**不能**以「上游成本 × 1.1」当软件基线。

---

## 二、计价优先级（已定方向）

按推荐优先级：

1. **任务额度**：一次标准导出 / 一次批处理（可按处理项数分档）。  
2. **月度套餐**：含一定任务量或处理项数。  
3. **团队额度池**：小团队共享。  
4. **超大任务增量**：超出套餐的处理项再确认后计费。  

### 用户界面应展示的语言

> 本次预计处理 36 项，消耗 1 个标准任务额度；若扩展到 200 项会再确认。

可选附带价值感：「大约帮你省下 N 分钟重复劳动」——**不要**展示上游 token 明细或供应商原始成本。

### 明确不建议首发

| 做法 | 原因 |
|------|------|
| 在上游 API 上加价约 **1.1 倍（~10% 毛利）** 作为软件基线 | 几乎盖不住支付、退款、支持、欺诈、失败重试、获客与工程；这是 **token 转售**，不是 Paw Work 业务 |
| 每一步按 token 跳动扣费 | 焦虑、难理解、与「完成任务」价值脱钩 |
| 强制用户选择 GPT / Claude / 等模型名 | 目标岗位不关心；增加配置感 |
| 对外主推 BYOK | 开发便利 ≠ 产品承诺；污染商店与信任叙事 |

### 毛利原则（业务语言）

- 目标是**软件业务级毛利**（历史上 GTM 稿中「数倍于上游成本」的量级方向可用于内部测算，**不是**写进 UI 的「加价倍数」话术）。  
- 健康毛利**主要来自**「一次理解样例 + 程序化批量 + 缓存与复用 + 本地生成交付物 + 失败限额」，而不是单纯抬价。  
- 单任务智能成本应随任务规模**亚线性**增长；若每条商品都完整走一遍大模型，任何加价都难同时做到快、便宜、可靠。  
- 支付通道、税费、退款与欺诈预留后，仍须有空间覆盖支持与产品迭代。

与旧稿关系：**废止**「平台在上游成本基础上加价约 1.1 倍」作为对外与执行基线；**废止**与之并存却互相矛盾的「仅 4–5x 叙事却又写 1.1x」双轨——统一到本文「任务计价 + 软件毛利」。

## 三、免费体验与付费墙

### 原则

1. **免费必须足以完成一次完整、正确、可下载的任务**（演示站或限项真实站均可）。  
2. 用户**先看到可用文件**，再遇到付费。  
3. 可用「演示页 / 项数上限 / 每日次数」控制滥用，而不是用「烧完 $0.20 就断在半截」制造挫败。  
4. 首次真实站点任务可设 **10–20 项**一类上限（实验区间）。  
5. 初期可并行试验：任务包、月度套餐、团队套餐——**不急于**唯一押宝大额预付余额。  

### 防滥用（与体验平衡）

- 登录门槛（如 Google 账号）可用于防刷，须说明对用户的好处（额度到账、跨设备）。  
- 设备 / IP 频次限制、新账户限额等作为运营手段保留，**不得**牺牲「第一次完整成功」。  
- 未消耗的预付余额可退；已消耗的服务资源不可退——规则用白话写清。

## 四、定价实验区间（假设，非市场事实）

以下仅供验证，需用真实省时与付费意愿校准：

| 档位 | 实验区间（示意） | 说明 |
|------|------------------|------|
| 个人轻量 | 约 ¥49–99 / 月 或等价任务包 | 低频整理与下载 |
| 高频个人 / 专业 | 约 ¥99–199 / 月 | 每周多次同类任务 |
| 小团队 | 约 ¥299–999 / 月 | 成员与任务池；模板与 onboarding 可另计 |

定价依据应是：

- 每月节省多少人工小时  
- 任务是否直接支持收入或交付  
- 错误造成的复核成本  
- 替代临时助理 / 外包的比例  
- 团队共享成功做法的价值

## 五、客户形态

**主路径：Prosumer / 小团队楔子**——有明确浏览器重复劳动的个人岗位与小团队，再扩张到团队管理、共享配方、审计与用量。

| 优先 | 不优先 |
|------|--------|
| 中小跨境电商、代运营与素材整理、采购与商品研究、内容运营工作室、高频处理商品/名单的助理 | 超大型企业首发、金融医疗政府高监管首发、无人值守夜间 RPA、外联刷量与绕过平台限制需求 |

纯广撒网 B2C 安装与信任成本高；大型企业采购周期过重。证据冲刺阶段以陪跑与小团队为主。

## 六、支付、主体与税务（候选方案，待专业验证）

> **重要：** 下列为历史讨论中的**候选方向**，涉及司法辖区、税收居民身份与实际经营地，**不能**由产品文档定论。商业启动前须咨询合格专业人士。公司注册**不是**验证产品价值的前置条件。

- **收款：** Merchant of Record（如 LemonSqueezy / Paddle 一类）是全球数字销售的常见候选，可降低自行处理多国销售税的负担；费率与覆盖范围以签约时条款为准。  
- **原生银行卡收单：** 全球合规成本可能显著，是否采用取决于主体与市场，不作本文事实断言。  
- **主体：** 美国 Delaware LLC 等曾被讨论为可选结构之一；早期应优先「能合法收款的最简结构」，避免为尚未出现的全球规模过度设计。  
- **购买力平价等：** 可作为后期增长手段实验，非 MVP 必选项。

## 七、风控与退款（原则级）

| 方向 | 说明 |
|------|------|
| 支付风控 | 启用支付方提供的欺诈防护与必要的 3DS 等（按通道能力） |
| 新账户限额 | 防止盗卡与批量注册刷免费；限额应在「完整免费任务」之上设计 |
| 退款 | 未消耗余额/额度可退；已完成任务消耗不退——用产品语言写清 |
| 失败任务 | 因产品责任导致的明显不可用结果，应有补额度 / 重试政策（具体规则上线前定） |

## 八、商业启动与产品验证的关系

证据冲刺（见 [`../STRATEGY.md`](../STRATEGY.md)）优先证明**留存、可靠度、付费意愿**。  
下列基础设施**可并行筹备**，但**不是**「没有就不能验证价值」的闸门：

- 商店审核通过  
- 账号与额度系统  
- 支付通道对接  
- 隐私政策与服务条款  
- 主体注册  

启动公开收费前的产品侧前提（业务语言）：

- [ ] 首个楔子任务达到可承诺可靠度与可核对交付  
- [ ] 免费路径可完成一次完整下载  
- [ ] 用量语言为任务/套餐，无 token 转售感  
- [ ] Consumer 主路径无对外 BYOK / 开发者主入口  
- [ ] 至少一条触达目标岗位的获客路径有正向信号
